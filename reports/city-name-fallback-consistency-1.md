## 1. Problem statement (user-reported)

Even after CITY-NAME-SEO-FALLBACK-POLICY-1 (`5e0e6d1`) which makes the SSR HTML render `Gwangju` everywhere via the central `_placeL10n.getLocalizedPlaceName` en-fallback chain, a user-captured screenshot of `/ur/prayer-times-in-gwangju` showed the page rendering **TWO different names for the same city**:

- `Gwangju` (Latin — the en-fallback per the central helper)
- `گوانگ جو` (Urdu transliteration — appearing in some surfaces)

This violates the unified-localization rule. The page must show ONE consistent value for the city across every position.

Per user policy:
- If `names[lang]` is missing from curated, the WHOLE page uses `names.en` Latin.
- No transliterated / generated / Nominatim-derived value (`گوانگ جو`) may appear unless that exact string lives in `curated-places.json` under `names.ur`. It does not.
- This phase fixes the inconsistency without mutating curated, without runtime translation, without fillchain.

---

## 2. Root cause (single source of `گوانگ جو`)

The Latin Urdu transliteration `گوانگ جو` was injected **after hydration** by client-side `js/app.js`:

1. **Client cold-load**: SSR HTML correctly renders `Gwangju` in every surface (`<title>`, H1, `__PRAYER_CITY__.name`, `<meta name="ssr-city-name">`). Verified: `curl /ur/prayer-times-in-gwangju | grep "گوانگ جو" = 0 hits`, `Gwangju = 26 hits`.
2. **Async path**: `js/app.js` calls `reverseGeocode(lat, lng, false)` against Nominatim with `Accept-Language: ur`. Nominatim returns `name:ur="گوانگ جو"` (its runtime phonetic transliteration of the Latin string "Gwangju" — generated by Nominatim's own engine).
3. **Globals updated**: callback writes `currentLocalizedName = "گوانگ جو"`.
4. **Surface override**: `getDisplayCity()` Tier-0 had a guard:
   ```js
   const _isAbsenceLang = (lang === 'ar' || lang === 'ur' || lang === 'bn');
   const _seedHasLatin = /[A-Za-z]/.test(_pc.name);
   if (!_isAbsenceLang || !_seedHasLatin) {
       return _pc.name;
   }
   // Absence-lang + Latin seed → fall through
   ```
   For Gwangju on `/ur/`: `_isAbsenceLang=true`, `_seedHasLatin=true` → falls through.
   Then later in the chain (line 851-855): `currentLocalizedName = "گوانگ جو"` passed `_isDisplayScriptAcceptable("گوانگ جو", "ur")` (Arabic-block present → true) → `getDisplayCity()` returned `"گوانگ جو"`.
5. **DOM walker propagation**: `_syncCityNameInDom()` then accepted `"گوانگ جو"` as `goodName` (passed the "non-Latin on absence-lang" filter) and walked the entire `<body>` replacing every `Gwangju` with `گوانگ جو`. The `<title>` element was untouched (head ≠ body), producing the inconsistency: title `"Gwangju میں…"` + body `"گوانگ جو میں…"`.
6. **`getCurrentCityLabel()` had the twin guard**, so any surface using it (#snb-city, #loc-hero-title, etc.) ALSO returned the transliteration.

The deliberate absence-lang fallthrough was introduced in PLACE-NAMES-TEMPLATE-CONSISTENCY-ALL-LANGS-FIX-1 (2026-05-18) BEFORE the central server-side helper existed. At that time, `_pickCuratedName` could return polluted `names.ur` (Latin in Urdu slot from legacy fillchain) — the fallthrough was a defense against the server bug. CITY-NAME-SEO-FALLBACK-POLICY-1 (2026-05-20, `5e0e6d1`) fixed the server side with the central `_placeL10n.getLocalizedPlaceName`. Once the server became correct, the client fallthrough became HARMFUL: it now rejects the canonical en-fallback and gives Nominatim's transliteration priority.

## 4. The fix (3 sites in `js/app.js` + cache-buster bump)

### 4.1 `getDisplayCity()` Tier-0 — unconditional trust when slug matches

Removed the `_isAbsenceLang && _seedHasLatin → fall through` branch from both the `__QIBLA_CITY__` path and the `__PRAYER_CITY__` path. The seed is now **always** returned when URL slug matches.

```diff
- if (_slugM && _slugM[1] === _pc.slug) {
-     const _isAbsenceLang = (lang === 'ar' || lang === 'ur' || lang === 'bn');
-     const _seedHasLatin = /[A-Za-z]/.test(_pc.name);
-     if (!_isAbsenceLang || !_seedHasLatin) {
-         return _pc.name;
-     }
-     // Absence-lang + fillchain Latin seed: fall through so PT-LANG-GUARD-2/3 below can decide
- }
+ if (_slugM && _slugM[1] === _pc.slug) {
+     return _pc.name;
+ }
```

### 4.2 `getCurrentCityLabel()` Tier-0 — twin fix

Same removal applied to both qibla and prayer-city paths in `getCurrentCityLabel()`.

### 4.3 `_syncCityNameInDom()` — REVERSE absence-lang guard

Added a new guard after the existing one:

```diff
  // Existing: Arabic ssrName + Latin goodName on absence-lang → don't replace
  if (_isAbsenceLang && !_hasLatin(ssrName) && _hasLatin(goodName)) return;

+ // NEW: Latin ssrName + non-Latin goodName on absence-lang → don't replace
+ // (stops Nominatim's transliteration "گوانگ جو" from walking over
+ // the canonical en-fallback "Gwangju" on /ur/ and /bn/ pages)
+ const _hasArOrBnEarly = /[؀-ۿঀ-৿]/.test(goodName);
+ if (_isAbsenceLang && _hasLatin(ssrName) && _hasArOrBnEarly) return;
```

### 4.4 Cache-buster bumped

`index.html`: `js/app.js?v=664` → `js/app.js?v=665` (both `<link rel="preload">` + `<script defer>` references).
